Архитектура системы «Бот + Бэктестер + Оптимизатор» :

Система будет состоять из трёх основных компонентов:

Торговый бот (работает в реальном времени) — периодически («on the fly») получает данные о ценах и сигналах, принимает решения по ребалансировке на основе текущей конфигурации (unified_config.json), выполняет сделки и отслеживает PnL и другие KPI. Конфигурация бота хранится в unified_config.json, в том числе разделы backtest_settings (параметры для бэктестера) и optimizer_settings (параметры оптимизатора). Бот при старте загружает эти настройки
GitHub
.

Бэктестер «futures_rebalance_backtester.py» — новый модуль (один файл), запускающийся раз в 24 часа (например, по расписанию). Он максимально переиспользует существующие модули (импортируя функции из rebalance_backtester.py, такие как load_signal_data() и run_backtest()), а также использует уже сохраняемые данные. Бэктестер считывает исторические данные о цене и сигналах из CSV-файлов (например, graphs/BTCUSDT_data.csv и graphs/BTC_signals.csv), имитирует торговлю с текущими параметрами и вычисляет метрики эффективности (PnL, sharpe_ratio, profit_factor и др. – полный список в коде 
GitHub
). Входные данные и сигналы загружаются так же, как в текущем бэктестере: путь к CSV задаётся шаблоном из конфига (например, graphs/{main_asset_symbol}_signals.csv
GitHub
), а функция load_signal_data() формирует столбец signal
GitHub
.

Модуль оптимизации — запускается при срабатывании триггеров. В роли оптимизатора может быть встроенный Optuna-модуль (например, rebalance_optimizer.py), который принимает на вход базовые параметры из unified_config["backtest_settings"] и цели оптимизации (критерий — прибыльность, Sharpe и т.д.). Оптимизатор генерирует варианты новых параметров (например, меняет rebalance_threshold, min_order_notional_usdt, min_rebalance_interval_minutes
GitHub
 и т.д.) и запускает для каждого бэктестер (run_backtest) для оценки. Функция objective() в коде оптимизатора показывает, как за счёт Optuna пробегается по параметрам и вызывает бэктестер
GitHub
.

Эти компоненты связаны между собой: бот хранит текущие параметры, бэктестер использует их для симуляции и получения метрик, а оптимизатор на их основе ищет улучшения. В итоге оптимизированные настройки (после проверки стабильности) могут автоматически применяться к бот-конфигу.

Алгоритм работы системы

Ежедневный запуск бэктестера. По расписанию (например, через cron или планировщик ОС) каждую 24 часа запускается futures_rebalance_backtester.py. Этот скрипт читает unified_config.json и берёт параметры из раздела backtest_settings
GitHub
GitHub
. Он определяет main_asset_symbol (например, BTC), подставляет его в шаблоны путей (*.csv) и загружает исторические данные о цене и сигналах (файлы graphs/XXX_data.csv и graphs/XXX_signals.csv)
GitHub
GitHub
.

Симуляция торговли. Бэктестер использует существующую логику ребалансировки (функцию run_backtest() или аналогичную) для имитации трейдинга: на каждом тиковом шаге учитываются входящие сигналы, проверяются условия ребалансировки, рассчитываются сделки, учитываются комиссии/проскальзывание и т.п. В результате моделирования вычисляются ключевые метрики: итоговый PnL в USD, рост капитала, максимальная просадка, коэффициент Sharpe и др.
GitHub
. Например, в коде перечислены метрики total_net_pnl_usdt, sharpe_ratio, profit_factor и т.д. 
GitHub
.

Проверка триггеров для оптимизации. После завершения бэктеста система проверяет, нужно ли обновлять параметры. Триггерами могут быть: низкая производительность (напр., PnL меньше нуля или ниже целевого), ухудшение KPI (например, низкий Sharpe или возросшая просадка), или по расписанию (например, каждый X дней) для поиска улучшений. Если срабатывает хотя бы один триггер, начинается процедура оптимизации параметров. Критерии и пороги задаются отдельно (например, метрика Sharpe выше заранее заданного значения).

Запуск оптимизатора. При триггере запускается модуль оптимизации, который варьирует только параметры из backtest_settings (такие как rebalance_threshold, min_order_notional_usdt, min_rebalance_interval_minutes, futures_leverage и т.п.)
GitHub
. Важное условие: не изменять другие разделы конфига (например, веса активов, частоту генерации сигналов) на этом этапе. Оптимизатор перебирает варианты по заданному простору (описанному в optimizer_settings.optimization_space в конфиге) и оценивает каждый с помощью бэктеста (функция run_backtest)
GitHub
. Лучший набор параметров выбирается на основе целевой метрики (например, максимизации Sharpe или PnL).

Подтверждение результатов. Новый набор параметров нельзя сразу применять в торговле. Для надёжности система запускает повторные бэктесты (на новых выборках данных) в течение «горячих» 72 часов, чтобы убедиться, что улучшения стабильны (нет переобучения на старых данных). То есть каждую 24 часа в следующие 3 дня снова симулируется торговля с найденными параметрами и сравниваются метрики. Если они подтверждаются (например, KPI всё так же на высоком уровне и нет случайных всплесков), то результаты считаются валидными.

Применение изменений. После успешной верификации лучшие параметры автоматически записываются в unified_config.json (раздел backtest_settings), перезаписывая старые
GitHub
GitHub
. Это «горячее» обновление конфигурации заставит бот начать использовать новые настройки с ближайшего старта. При этом в конфиге должна быть опция (флаг) для возможности отключения авто-применения (если нужно тестировать вручную).

Продолжение работы. Бот получает обновлённый конфиг и работает с новыми параметрами. Через сутки цикл повторяется: снова бэктестер проводит симуляцию с обновлёнными настройками, проверяет эффективность, и при необходимости оптимизирует дальше.

План разработки кода

Создать модуль futures_rebalance_backtester.py. В нём реализовать функцию main(), которая будет вызываться по расписанию. main() должен принимать (или жёстко задавать) путь к unified_config.json, загружать его и извлекать backtest_settings
GitHub

Переиспользовать существующие функции. Импортировать из rebalance_backtester.py или других модулей функции загрузки данных и симуляции. Например, вызвать load_signal_data(path) для сигнальных CSV
GitHub
 и run_backtest(params, data_path) для запуска симуляции
GitHub
. Это позволит избежать дублирования логики. При необходимости адаптировать их под «futures-only» сценарий (например, заранее включить apply_signal_logic: true, учесть futures_leverage и т.п. 
GitHub
).

Реализовать логику триггеров. После получения метрик от симуляции нужно сравнить их с порогами. Например, хранить в конфиге значения-ориентиры PnL/KPI или рассчитывать изменение относительно предыдущего бэктеста. Если условие срабатывает, вызвать оптимизатор.

Интеграция оптимизатора. Использовать модуль оптимизации (Optuna) для изменения параметров. Можно заимствовать код из rebalance_optimizer.py: там в функции objective() показано, как изменения попадают в бэктестер
GitHub

Многократная проверка стабильности. Для подтверждения результатов за следующие 72 часа запланировать повторные запуски бэктестера с новыми настройками (это может быть тот же модуль, просто параметризированный новым конфигом). Автоматически оценивать, что метрики не упали ниже целевых. Если какие-то дни оказываются неудачными, можно либо отменять оптимизацию, либо проводить дополнительный поиск.

Применение и обновление конфига. После успешного подтверждения автоматически перезаписать unified_config.json: заменить старые backtest_settings на новые. Для этого можно использовать стандартную работу с JSON-файлами (чит/запись). Необходимо убедиться, что остальные разделы конфига (например, стратегии, сигналы, веса) не меняются. В конфиге предусмотреть флаг (например, auto_apply: true/false), чтобы отключать или включать автоматическое применение новых настроек.

Логирование и отчёты. Вести детальный лог работы модуля — какие решения приняты, какие параметры проверялись и применялись. Результаты бэктестов можно сохранять в отчёты для анализа. Уже существующий механизм report_path_prefix
GitHub

План тестирования

Юнит-тесты бэктестера. Проверить, что run_backtest корректно учитывает входные сигналы и выполняет расчёты. Например, дать простой CSV с известными данными и сигналом «BUY» в начале, убедиться, что появляется сделка и PnL считается верно. Можно протестировать крайние случаи (пустой сигнал, короткие позиции, срабатывание «circuit breaker» и т.п.). Функция simulate_rebalance уже изолирована и её можно протестировать отдельно.

Юнит-тесты оптимизатора. Проверить функцию objective() на единичных примерах — например, смоделировать несколько тривиальных случаев, где известен «лучший» параметр. Убедиться, что она вызывает бэктест с подставленными значениями (можно подменить run_backtest на заглушку и проверить аргументы). Также протестировать, что при отсутствии run_backtest или данных происходит Pruning (например, срабатывание TrialPruned
GitHub
).

Тест интеграции. Создать упрощённый конфиг (наподобие dummy из main()
GitHub
) и симулированные данные (или взять реальные небольшие фрагменты CSV) и запустить futures_rebalance_backtester.py. Проверить, что он корректно читает конфиг и данные, производит симуляцию и выводит метрики. Затем имитировать запуск оптимизации, замещая поиск небольшим перебором, и убедиться, что новые настройки применяются только в backtest_settings.

Тест «горячей» перезаписи конфига. Проверить сценарий, когда оптимизация успешна и параметры подтверждены, и модуль меняет unified_config.json. Убедиться, что изменения видны в файле и бот при следующем старте использует новые значения. Также протестировать флаг отключения (при auto_apply=false – изменения не должны применяться).

Энд-ту-энд тестирование. На подготовленных исторических данных запустить цепочку: бот-симулятор (с начальным конфигом) – бэктестер – оптимизатор – бэктестер (повтор) – обновление. Следить, что параметры меняются логично и улучшения действительно достигаются. Например, в тестах можно предусмотреть известные ситуации, где изменение rebalance_threshold повышает PnL, и убедиться, что система его находит.

На каждом шаге разработки и тестирования важно опираться на существующие модули как на «золотой стандарт». Код бэктестера должен, где возможно, вызывать функции из rebalance_backtester.py, а оптимизатор — из rebalance_optimizer.py. Это обеспечит согласованность логики с уже отлаженными частями проекта.
