# Анализ и описание futures_rebalance_backtester.py

Этот скрипт представляет собой комплексную систему для тестирования торговых стратегий на исторических данных. Он загружает параметры из конфигурационного файла, обрабатывает рыночные данные и торговые сигналы, симулирует исполнение стратегии и генерирует подробные отчеты.

## Ключевые функции и их связи:

### `run_backtest(params_dict, data_path, ...)` — Главная функция

*   **Назначение:** Ядро бэктестера. Оркестрирует весь процесс от загрузки данных до расчета финальных метрик.
*   **Связи:** Вызывает практически все остальные функции (`load_data`, `load_signal_data`, `calculate_portfolio_value`, `record_trade`, `compute_metrics`, `simulate_rebalance`).

### `load_data(csv_path)` и `load_signal_data(signal_csv_path)`

*   **Назначение:** Вспомогательные функции для загрузки и предварительной обработки рыночных данных (цен) и торговых сигналов из CSV-файлов.
*   **Связи:** Вызываются в начале `run_backtest`.

### `record_trade(...)`

*   **Назначение:** Функция-логгер. Записывает информацию о каждой попытке совершить сделку в основной список сделок (`trades_list`).
*   **Связи:** Вызывается внутри главного цикла `run_backtest` каждый раз, когда логика ребалансировки генерирует ордер.

### `compute_metrics(df_eq, trades, ...)`

*   **Назначение:** Рассчитывает итоговые метрики производительности (Sharpe, Sortino, Max Drawdown и т.д.) на основе данных о динамике портфеля (`df_eq`) и списка сделок.
*   **Связи:** Вызывается в конце `run_backtest`.

### `simulate_rebalance(data, orders_by_step, ...)` — Внешний симулятор PnL

*   **Назначение:** Это вторая, параллельная система симуляции. Она принимает на вход ордера, сгенерированные в основном цикле, и независимо рассчитывает PnL по ним, усредняя цены входа и закрывая позиции.
*   **Связи:** Вызывается в конце `run_backtest`.
*   **Важное замечание:** Результаты этой функции (`simulated_trade_log`) используются только для генерации отчета `rebalance_trades.csv`. Основные метрики производительности, такие как `total_net_pnl_usdt`, рассчитываются на основе другой логики внутри `run_backtest`. Это архитектурная странность, так как в системе по сути два разных механизма расчета PnL.

### `main()` и `run_standalone_backtest(...)`

*   **Назначение:** Обеспечивают запуск бэктестера как самостоятельного скрипта из командной строки, обрабатывая аргументы и загружая конфигурационный файл.

## Алгоритм работы `run_backtest`:

### 1. Инициализация:

*   Глубокое копирование параметров, чтобы избежать изменения исходного конфига.
*   Загрузка и обработка всех настроек: плечо, веса, пороги, пути и т.д.
*   Создание словаря `portfolio` для хранения состояния портфеля (баланс, кол-во активов, PnL и т.д.).

### 2. Загрузка данных:

*   Загружаются исторические цены и торговые сигналы.
*   Данные о сигналах объединяются с рыночными данными, чтобы на каждой свече был известен актуальный сигнал.

### 3. Основной цикл (по свечам):

*   Скрипт итерируется по каждой строке (свече) в исторических данных.
*   **Расчет PnL:** На каждом шаге вычисляется нереализованный PnL по открытым фьючерсным позициям на основе изменения цены с предыдущей свечи.
*   **Обновление состояний:** Номинальная стоимость фьючерсных позиций обновляется на сумму PnL.
*   **Расчет NAV (Net Asset Value):** Вычисляется общая стоимость портфеля (как мы выяснили, по некорректной формуле, которую исправили для Safe Mode).
*   **Проверка Safe Mode:** На основе исправленной логики расчета маржи и NAV, система проверяет, не нужно ли войти в "Безопасный режим" или выйти из него. В зависимости от режима, выбираются соответствующие целевые веса (`target_weights_normal` или `target_weights_safe`).
*   **Проверка необходимости ребалансировки:** Система проверяет, не превысило ли отклонение текущих весов от целевых заданный порог (`rebalance_threshold`) и не было ли сделок в пределах `min_rebalance_interval_minutes`.
*   **Генерация сделок:** Если ребалансировка нужна, вычисляются необходимые корректировки для каждого актива.
*   **Проверка по сигналам:** Если `apply_signal_logic` включен, система блокирует сделки, противоречащие сигналу (например, продажу на сигнале 'BUY').
*   Сгенерированные сделки записываются в `trades_list` через `record_trade` и добавляются в `orders_by_step` для второй симуляции.
*   **Запись динамики Equity:** Текущая стоимость портфеля добавляется в историю (`equity_over_time`).

### 4. Пост-обработка:

*   **Вторая симуляция:** Вызывается функция `simulate_rebalance`, которая на основе `orders_by_step` проводит свой, альтернативный расчет PnL и сохраняет его в `rebalance_trades.csv`.
*   **Расчет метрик:** Вызывается `compute_metrics` для расчета итоговых KPI на основе данных из основного цикла.
*   **Генерация отчетов:** Все метрики, сделки и графики сохраняются в папку с отчетами.
