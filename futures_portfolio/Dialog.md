Почему обычно берут маркировочную / lastPrice, а не close(1m)
Маркировочная цена и lastPrice ближе к реальности в реальном времени
При отслеживании риска ликвидации тебе важно знать, насколько близко сейчас цена к ликвидационной.

lastPrice — это фактическая цена последней сделки прямо сейчас.

markPrice (маркировочная) — это расчётная цена, на основе которой считается ликвидация на Binance Futures; именно она «заряжает» риск, а не цена свечи.

close(1m) — это цена сделки, которая была в конце прошлой минуты, то есть уже устаревшая на несколько секунд/десятков секунд.

Ликвидация считается по markPrice, а не по kline‑close
Binance рассчитывает ликвидационную цену и маржу на основе текущей маркировочной цены, а не на основе закрытий свечей.
Если ты будешь ориентироваться на close(1m), то:

можешь запаздывать на 15–60 секунд,

и промахнуться по моменту, когда цена уже реально приблизилась к ликвидации.

Minute‑close — это хороший сигнал, но не для ликвидационного мониторинга
close(1m) отлично подходит:

для ребалансировки по таймфрейму,

для фильтрации шума и стратегических решений,
но не для быстрого контроля риска, где каждый пиксель и каждый удар по рынку важен.

Как совместить оба подхода
Можно сделать так:

Для мониторинга ликвидации (high‑priority):

каждые 1–5 секунд считать:

markPrice и/или lastPrice,

расстояние до ликвидационной цены по формуле Binance.

если приближение до ликвидации, сразу уменьшать риск этой ноги.

Для ребалансировки портфеля (low‑priority):

каждые 15 минут считать по закрытию 15m‑свечи (или хотя бы 1m/5m‑close),

на основе этих close пересчитывать доли портфеля и запускать ребаланс только если:

нет критического риска ликвидации,

и отклонение доли ≥ 3.5%.

То есть:

маркеры/lastPrice — для быстрой реакции на риск ликвидации,

цены закрытия свечей — для спокойного ребаланса портфеля без лишнего дребезга.

Если хочешь, могу помочь придумать конкретные формулы/пороги для расчёта «дистанции до ликвидации» под твой плечевой 5× и используемые вампирные контракты.

Отличный момент: тебе нужно стабильность в логах, а не дергание стоимостей долей из‑за микро‑шума. Это решается разделением целей:

что‑то считать он‑лайн, быстро, для риска ликвидации,

а что‑то считать спокойно и редко, для логов и ребаланса.

Как добиться «не скакающих» стоимостей долей в логах
Считай лог‑стоимости по закрытиям свечей, а не по тикам
Для логов долей портфеля фиксируй параметры только:

в момент закрытия определённой свечи (например, 15m или 1h),

или при событии ребаланса.

То есть:

берёшь close свечи,

пересчитываешь:

текущий размер каждой позиции (в контрактах),

умножаешь на close → получаешь стоимость доли в USDT,

и именно это значение пишешь в лог.

Тогда логи:

не «дребезжат» внутри свечи,

отражают только структуру портфеля в фиксированные моменты времени.

Для ликвидационного мониторинга считай отдельно, без логов каждой секунды

риск ликвидации следи он‑лайн (каждые 1–5 секунд) по markPrice/lastPrice,

но в логах не пиши каждый новый процент к ликвидации.

Логируй:

«приблизился к ликвидации» (YES/NO),

какое было максимальное приближение за период,

и сам факт коррекции позиции (сколько контрактов уменьшил/добавил).

Это даёт тебе операционную картину риска, но без шума в стоимостях долей.

Жёстко зафиксируй «точку отсчёта» для стоимости доли
Например, сделай правило:

«Стоимость каждой доли портфеля в логах фиксируется ТОЛЬКО по закрытию 15m‑свечи и при ребалансе; внутри свечи для логов новые значения не меняются».

Это:

убирает скачки в логах,

оставляет тебе чистую картину по таймфрейму.

Пример структуры строки лога
text
YYYY-MM-DD HH:MM:SS | timeframe=15m | TF_close=90000 | 
  long_contracts=2.5 | long_value=225000 | long_pct=49.8% |
  short_contracts=2.5 | short_value=225000 | short_pct=49.8% |
  rebalance=NO | liquidation_risk=OK
long_value, short_value, *_pct считаются только по закрытию свечи,

liquidation_risk — бинарный флаг/статус, без точных дробных значений.

в логах считать EMA(3–5 последних закрытий) вместо «чистого» close,

Итого:

Да, ты правильно формулируешь логику — и именно так можно её разделить на два режима:

1. Ребаланс по риску ликвидации (aggressive)
Условия:

Есть приближение к ликвидационной цене (например, расстояние до ликвидации ≤ X % от шага позиции).

При этом достигнут порог отклонения доли портфеля (например, ≥ 3.5%).

Тогда:

Ребаланс выполняется немедленно, без ожидания старшего таймфрейма.

Используется текущая цена (markPrice / lastPrice) для расчёта:

направления коррекции,

и размера позиции, чтобы не уйти в ликвидацию.

В логах фиксируешь:

факт «риск ликвидации + превышение порога»,

и саму цену в момент ребаланса (например, markPrice или lastPrice),

но не переписываешь каждый тик — только сам факт и параметры.

2. Обычная ребалансировка (regular)
Условия:

Нет критического риска ликвидации (например, расстояние до ликвидации > X %).

Достигнут процентный порог отклонения доли портфеля (например, ≥ 3.5%).

При этом прошла фиксированная точка старшего таймфрейма (например, закрытие 15m или 1h свечи).

Тогда:

Ребаланс выполняется по расписанию (раз в 15/60 минут и т.п.).

Для расчёта стоимости долей используется цена закрытия этой старшей свечи (close),

чтобы значения в логах были стабильными и не скакали внутри периода.

В логах:

фиксируешь только закрытие свечи и значения долей на этот момент,

без перерасчёта при каждом тике.
