**Текущий расчёт на базе INJUSDT:**
- Реальный PnL: +7.21% за 37 часов ≈ +4.7% за 24ч (экстраполяция)
- Бэктест 1д: +35.53% (теоретический максимум)
- Бэктест 30д: +34.37% → ~1.1% в день (среднее)

**Для достижения 5%/день необходимо:**
1. 3+ REAL бота с разными тикерами (диверсификация)
2. initial_capital ≥ 100 USDT на бота
3. Тикеры из топ-50 бэктеста с min_cycles > 50
4. Стабильная работа без простоев (heartbeat < 15 мин)

**Прогноз при 3 ботах × 5%/день:** эквити системы × 1.05³ ≈ +15.8% в день (компаунд).

### Методология ранжирования

Каждый баг оценён по 4 критериям (шкала 1–5):

| Критерий | Описание | Вес |
|----------|----------|-----|
| **Impact (I)** | Влияние на PnL / безопасность / стабильность | ×3 |
| **Probability (P)** | Вероятность срабатывания в продакшене | ×2 |
| **Detection (D)** | Сложность обнаружения (1 = очевидно, 5 = скрытый) | ×1 |
| **Effort (E)** | Сложность фикса (часы) — делитель | ÷1 |

**Score = (I×3 + P×2 + D×1) / E** → чем выше, тем приоритетнее фикс.

### Детальный анализ каждого бага

#### B1: TS flag persistence — КРИТИЧЕСКИЙ

**Проблема:** После срабатывания trailing stop и рестарта supervisor, флаг `trailing_stop_triggered: true` сохраняется в real_state JSON. При следующем запуске бот видит флаг и пропускает проверку TS на каждом heartbeat: `"Skipping trailing stop check"`.

**Цепочка сбоя:**
```
TG blocks rebalance → equity drops → TS triggers → restart →
→ TS flag stuck → protection dead → equity drops further → NO TS protection
```

**Impact:** 5 — Полная потеря защиты депозита. Без TS бот может слить весь баланс.
**Probability:** 4 — Любой рестарт supervisor (обновление, краш, плановый) активирует баг.
**Detection:** 3 — Видно в логах ("Skipping trailing stop check"), но только если знать что искать.
**Effort:** 3 — Добавить сброс флагов в supervisor.py при рестарте после TS.

**Фикс:**
```python
# supervisor.py — при рестарте после TS
if real_state.get("trailing_stop_triggered"):
    real_state["trailing_stop_triggered"] = False
    real_state["trailing_stop_violation_start"] = 0.0
    save_state(real_state)
```

#### B8: Liquidation guard не работает при кросс-марже — КРИТИЧЕСКИЙ

**Проблема:** Binance API не возвращает `liquidationPrice` для позиций на кросс-марже. `get_position_risk()` возвращает `liq_price: 0.0`. Liquidation guard не может рассчитать расстояние до ликвидации.

**Impact:** 5 — При экстремальном движении (>30% за минуты) позиция ликвидируется без предупреждения.
**Probability:** 3 — Редко, но возможно (см. PORTALUSDT +17% за 1ч, EPICUSDT).
**Detection:** 2 — Очевидно при ликвидации, но уже поздно.
**Effort:** 8 — Требует перехода на Isolated margin ИЛИ реализации собственного расчёта через mark price + margin balance.

**Варианты фикса:**
1. **Переход на Isolated margin** — Binance даёт liquidationPrice. Но: сложнее управление маржей.
2. **Собственный расчёт** — `liq_price ≈ mark_price × (1 ± 1/leverage)` для кросс-маржи. Приблизительно.
3. **Margin ratio как прокси** — при margin_ratio < 2.0x → emergency close. Уже реализовано.

**Рекомендация:** Вариант 3 уже работает. Увеличить частоту проверки margin_ratio до каждого heartbeat.

#### B7: Qty asymmetry — ВЫСОКИЙ

**Проблема:** LONG и SHORT открываются по разным ценам (spread, slippage). При x7 леверидже и 75 USDT capital:
- LONG entry: $49.95 / price_L → qty_L
- SHORT entry: $49.95 / price_S → qty_S
- При spread 0.1%: qty_L ≠ qty_S → несимметричный хедж

**Накопительный эффект:** Каждый цикл добавляет рассинхрон. После 100 циклов PnL drag может достигать 1–3%.

**Impact:** 4 — Постоянная потеря PnL, растёт со временем.
**Probability:** 5 — Происходит на каждом цикле.
**Detection:** 3 — Видно в логах (разный qty), но не очевидно без анализа.
**Effort:** 6 — Требует изменения логики расчёта qty в calculator.py.

**Фикс:** Рассчитывать qty для обеих сторон от единого notional:
```python
target_notional = capital * share * leverage
qty_long = target_notional / mark_price
qty_short = qty_long  # Симметрия
```

#### B6: config.json race-condition — ВЫСОКИЙ

**Проблема:** main.py (внутри бота) пишет в config.json напрямую (строки 130-138: удаление из live_swarm, добавление в toxic). Supervisor.py тоже пишет в config.json (строка 812: `safe_save_json`). Результат: запись от main.py перезаписывается supervisor.

**Impact:** 4 — Потеря toxic-записей → тикер с ликвидацией может быть запущен повторно.
**Probability:** 4 — При каждом срабатывании TS или liquidation guard.
**Detection:** 4 — Скрытый. Только при расследовании инцидентов.
**Effort:** 5 — Требует рефакторинга: единая точка записи или file-lock.

**Фикс:** Внедрить `file_lock` для всех операций записи в config.json:
```python
import filelock
lock = filelock.FileLock("config.json.lock")
with lock:
    config = load_config()
    # ... изменения ...
    save_config(config)
```

#### B3: exit-флаг не создаёт toxic-запись — СРЕДНИЙ

**Проблема:** main.py при прибыльном TS вызывает `emit_signal("exit", ticker)` → создаёт `exit_INJUSDT.flag`. Supervisor ищет только `stop_*.flag`. Exit-флаг удаляется без записи в toxic_blacklist.

**Impact:** 3 — Тикер после прибыльного TS может быть запущен повторно.
**Probability:** 3 — Только при срабатывании TS (сейчас TS отключён, но может быть включён).
**Detection:** 3 — Видно в логах, но только при активном мониторинге.
**Effort:** 3 — Добавить обработку `exit_*.flag` в supervisor.py.

**Фикс:**
```python
# supervisor.py — добавить обработку exit-флагов
exit_flags = glob("exit_*.flag")
for f in exit_flags:
    ticker = f.stem[5:]  # убрать "exit_"
    toxic_blacklist[ticker] = now + cooldown_sec
```

#### B4: HEAL перезапускает бот после trailing stop — СРЕДНИЙ

**Проблема:** `enforce_swarm_consistency()` проверяет позиции на бирже. Если позиция есть и state валиден → HEAL → `start_bot(ticker, is_paper=False)`. После TS позиции закрыты, но state может быть не обновлён.

**Impact:** 4 — Бот открывает позиции заново после штатного закрытия.
**Probability:** 2 — Только при определённом порядке событий (TS → supervisor restart до обновления state).
**Detection:** 3 — Видно в логах ("HEAL: restarting real bot").
**Effort:** 4 — Добавить проверку `trailing_stop_triggered` перед HEAL.

---

#### B2: Profit Guard + Drawdown Protection = вечный бот — СРЕДНИЙ

**Проблема:** Цепочка guards в supervisor.py (строки 285-310):
- `score == INF` (drawdown) → LOCKED IN COMBAT → пропустить
- `profit > 0` → Profit Guard → пропустить
- Результат: бот не может быть заменён ни при каких условиях.

**Impact:** 3 — Ротация парализована. Убыточный бот может работать бесконечно.
**Probability:** 3 — При длительной работе с одним тикером.
**Detection:** 2 — Очевидно при анализе логов ротации.
**Effort:** 6 — Требует пересмотра логики guards.

**Фикс:** Добавить возрастной лимит: `if age > max_age_days AND profit < replacement_threshold → force_replace`.

---

#### B5: Invariant Gate добавляет обратно в live_swarm — НИЗКИЙ

**Проблема:** `enforce_invariant_gate()` вызывается 2 раза за цикл. Если тикер удалён из live_swarm, но позиция ещё не закрыта — Invariant Gate вернёт его обратно.

**Impact:** 2 — Невозможно удалить тикер с открытой позицией.
**Probability:** 2 — Только при ручном удалении тикера.
**Detection:** 2 — Очевидно в логах.
**Effort:** 4 — Добавить флаг `force_remove` для ручных операций.

## 📋 Реестр решений (ADR)

### ADR-001: VIRTUAL OFF (03.06.2026)
- **Контекст:** VIRTUAL нога (35% TPV) вызывала паразитический ребаланс при сильных движениях.
- **Решение:** Отключена. Чистый 50/50 LONG/SHORT.
- **Последствия:** Снижение сложности, повышение предсказуемости.

### ADR-002: Trailing Stop отключён (08.07.2026)
- **Контекст:** TS=3.7% + activation=6.5% = зазор 2.8%. Ложные срабатывания на шуме.
- **Решение:** TS отключён (100/1000). Защита через guards.
- **Последствия:** Нет автоматического закрытия в прибыли. Ручной мониторинг.

### ADR-003: Кросс-маржа вместо Isolated (03.06.2026)
- **Контекст:** При 50/50 хедже Isolated маржа изолировала позиции, усложняя управление.
- **Решение:** Кросс-маржа. Вся маржа аккаунта = залог.
- **Последствия:** Liquidation guard не работает (Binance не даёт liquidationPrice для CROSS).

### ADR-004: Score-driven ротация (03.06.2026)
- **Контекст:** Старая ротация могла оставить <20 ботов при высоком пересечении сканера.
- **Решение:** Прибыльные боты (profit > 0) всегда остаются. Заменяются только убыточные.
- **Последствия:** Profit Guard может удерживать бота бесконечно (см. B2).
